Leanwork Group · Arquitetura .NET · v1.0

Lean Modular Architecture

Arquitetura API-first para .NET que vai direto ao ponto. Isola o que muda de verdade — e o que muda é a infraestrutura externa, não o banco. Do MVP de duas semanas ao sistema com 15 devs, a estrutura é a mesma.

01 — A ideia

Isole o que muda de verdade.

Clean Architecture isola tudo por via das dúvidas. A LMA isola só o que realmente troca — e cobra o preço de cada abstração antes de aceitá-la.

Separe por módulo de negócio e por ação. Isole o que muda de verdade — e o que muda é a infraestrutura externa, não o banco. Otimize para que a estrutura seja previsível e gerável.

Princípio fundador — LMA v1.0
01

Modularidade por negócio

O código se organiza por bounded context — Catálogo, Checkout, Faturamento — e não por camada técnica. Cada módulo é coeso, tem seu vocabulário e pode até ter o próprio banco.

02

Isolamento seletivo

Gateway de pagamento, storage e mensageria ficam atrás de interface, porque a volatilidade é real. Persistência não. O banco raramente troca — e quando troca, é refactor consciente, não abstração preventiva.

03

Humanos e IA

Boa parte do código hoje é escrita com LLM. A LMA assume isso como premissa de design: estrutura previsível, vocabulário fixo, decisões já tomadas. Menos ambiguidade, menos variação inventada.

Para que serve

  • APIs .NET em que a API é o produto, não um detalhe técnico.
  • Projetos rápidos — MVP, prova de conceito, SaaS inicial — que precisam de qualidade desde o dia 1.
  • Sistemas duradouros — ERP, marketplace, fintech, plataforma B2B — que precisam evoluir sem virar bagunça.
  • Times mistos onde a IA participa ativamente da geração de código.
  • Sistemas modulares com múltiplos bancos — um por módulo, cada um no workload certo.

02 — O código

Uma Ação. Um método. Um retorno.

Uma Ação é um vertical slice: uma classe, um método Execute, retorno Result<T>. Sem Handler, sem Service, sem MediatR, sem Repository. O exemplo abaixo é o código que sai do template, sem edição.

src/MinhaApi.Api/Modulos/Produtos/CriarProduto/CriarProduto.cs 
public class CriarProduto(AppDbContext db, ILogger<CriarProduto> logger)
{
    public async Task<Result<CriarProdutoResponse>> Execute(
        CriarProdutoRequest request,
        CancellationToken ct)
    {
        // Regra de negócio vive no Domain, não aqui.
        var resultado = Produto.Criar(
            request.Nome, request.Descricao, request.Preco, request.EstoqueInicial);

        if (resultado.IsFailure)
            return Result.Failure<CriarProdutoResponse>(resultado.Error!);

        var produto = resultado.Value!;
        db.Produtos.Add(produto);
        await db.SaveChangesAsync(ct);   // commit sempre explícito

        logger.LogInformation(
            "CriarProduto: produto criado. Id={ProdutoId}", produto.Id);

        return Result.Success(new CriarProdutoResponse(
            produto.Id, produto.Nome, produto.Preco, produto.EstoqueDisponivel));
    }
}

A Ação injeta AppDbContext direto. Não conhece HTTP, não valida formato e não chama outra Ação.

src/MinhaApi.Api/Endpoints/ProdutosEndpoints.cs 
public static class ProdutosEndpoints
{
    // TODAS as rotas do módulo Produtos vivem neste arquivo.
    public static IEndpointRouteBuilder MapProdutosEndpoints(this IEndpointRouteBuilder app)
    {
        var grupo = app.MapGroup("/produtos")
            .WithTags("Produtos")
            .AddEndpointFilter<ValidationFilter>();   // validação automática

        grupo.MapPost("/", async (
            CriarProdutoRequest body,
            CriarProduto acao,
            CancellationToken ct) =>
        {
            var resultado = await acao.Execute(body, ct);
            return resultado.IsSuccess
                ? Results.Created($"/produtos/{resultado.Value!.Id}", resultado.Value)
                : Results.BadRequest(resultado.Error);
        })
        .WithName("CriarProduto")
        .WithSummary("Cria um novo produto");

        return app;
    }
}

É aqui que o protocolo web é resolvido: JWT, headers, route params. A Ação recebe tudo limpo no Request.

src/MinhaApi.Domain/Modulos/Produtos/Produto.cs 
public class Produto
{
    public Guid Id { get; private set; }
    public string Nome { get; private set; } = string.Empty;
    public decimal Preco { get; private set; }
    public int EstoqueDisponivel { get; private set; }
    public bool Ativo { get; private set; }

    private Produto() { }   // EF Core reidrata por aqui

    public static Result<Produto> Criar(string nome, string descricao, decimal preco, int estoque)
    {
        if (string.IsNullOrWhiteSpace(nome))
            return Result.Failure<Produto>("Nome é obrigatório");

        if (preco <= 0)
            return Result.Failure<Produto>("Preço deve ser maior que zero");

        return Result.Success(new Produto { /* ... */ });
    }

    public Result ReservarEstoque(int quantidade)
    {
        if (!Ativo)
            return Result.Failure("Produto inativo não pode ter estoque reservado");

        if (EstoqueDisponivel < quantidade)
            return Result.Failure($"Estoque insuficiente. Disponível: {EstoqueDisponivel}");

        EstoqueDisponivel -= quantidade;
        return Result.Success();
    }
}

Setters privados, construtor privado, factory Criar. Estado só muda por método de negócio — e este projeto não referencia EF, ASP.NET nem FluentValidation.

src/MinhaApi.Api/Modulos/Produtos/CriarProduto/CriarProdutoModels.cs 
public record CriarProdutoRequest(
    string Nome, string Descricao, decimal Preco, int EstoqueInicial);

public record CriarProdutoResponse(
    Guid Id, string Nome, decimal Preco, int EstoqueDisponivel);

// Roda no IEndpointFilter, antes da Ação. Se falhar, retorna 400
// e a Ação nem chega a ser chamada.
public class CriarProdutoValidator : AbstractValidator<CriarProdutoRequest>
{
    public CriarProdutoValidator()
    {
        RuleFor(x => x.Nome).NotEmpty().MaximumLength(200);
        RuleFor(x => x.Preco).GreaterThan(0);
        RuleFor(x => x.EstoqueInicial).GreaterThanOrEqualTo(0);
    }
}

Request, Response e Validator na mesma pasta da Ação. Pasta plana, sem subpastas — a fatia inteira cabe em um ls.

03 — As regras

O compilador é o guardião.

Dois projetos físicos desde o dia 1. Não é convenção que o code review pega depois — é barreira de build. O que a IA não pode fazer, ela não consegue fazer.

MinhaApp.Api

Endpoints, Ações, Infrastructure. Minimal API, EF Core, Dapper, FluentValidation, Serilog, OpenTelemetry.

referencia

MinhaApp.Domain

Entidades ricas, Value Objects, Domain Services e Result<T>. Zero PackageReference de infraestrutura. Projeto puro.

Os 7 “nunca faça”

  • Ação nunca injeta outra Ação.
  • Domain nunca importa framework de infraestrutura.
  • Ação nunca vê HttpContext ou ClaimsPrincipal.
  • Nunca criar Repository ou Writer.
  • Ação nunca declara a própria rota.
  • Ação nunca valida formato manualmente.
  • Ação de escrita nunca retorna sem SaveChangesAsync(ct).

Os anti-padrões

Cada regra existe porque há um jeito tentador de quebrá-la. Estes são os oito desvios mais comuns — e a correção de cada um.

01 Ação injetando outra Ação 
public class ProcessarPedido(AppDbContext db, CalcularFrete outraAcao) { }

Correção: consulta direta ao banco, ou mover a lógica compartilhada para um Domain Service. Fatias não se acoplam.

02 Domain referenciando infraestrutura 
// em MinhaApp.Domain
using Microsoft.EntityFrameworkCore;

Correção: não compila se os projetos estiverem separados corretamente. Se você precisa de EF ali, a lógica está no projeto errado.

03 Protocolo web vazando para a Ação 
public class ProcessarPedido(AppDbContext db, IHttpContextAccessor http) { }

Correção: extrair o dado no Endpoint e passar limpo no Request. A Ação recebe ClienteId, não o JWT.

04 Reintroduzir Repository 
public interface IPedidoRepository { }

Correção: acesso direto via AppDbContext ou Dapper na Ação. Integração externa continua com interface — isso não é Repository.

05 Validação manual dentro da Ação 
if (string.IsNullOrEmpty(req.Nome))
    return Result.Failure(...);   // já foi feito no filtro

Correção: validação de formato fica no Validator, que roda no IEndpointFilter. Na Ação, só regra de negócio — e ela vive no Domain.

06 Ação declarando a própria rota 
public class ProcessarPedido
{
    public static void Map(IEndpointRouteBuilder app) => app.MapPost(...);
}

Correção: roteamento centralizado em Endpoints/{Modulo}Endpoints.cs. A Ação não conhece HTTP.

07 Commit implícito ou esquecido 
db.Pedidos.Add(pedido);
return Result.Success(...);   // nada foi persistido

Correção: await db.SaveChangesAsync(ct) explícito na última linha transacional da Ação de escrita.

08 Abstrair persistência “por via das dúvidas” 
// criar IDbContext, IUnitOfWork genérico etc. para "desacoplar o EF"

Correção: a LMA assume que o banco não troca. A abstração que paga aluguel é a de integração externa, não a de banco.

04 — Adequação

Quando usar. E quando não.

Nenhuma arquitetura serve para tudo. A LMA cobre uma gama ampla de projetos API-first em .NET — mas há casos em que outra abordagem paga melhor, e vale dizer isso em voz alta.

Use a LMA quando

  • Você constrói uma API .NET e ela é o produto.
  • Quer MVP rápido sem perder qualidade arquitetural — pasta plana e zero cerimônia entregam isso.
  • Tem um sistema grande, com muitos módulos e times, e precisa que a modularidade segure a complexidade.
  • Espera evolução longa e quer um esqueleto que sustente crescimento sem virar bagunça.
  • Tem múltiplos bancos por módulo — Postgres, Mongo, ClickHouse. Isso é primeira classe na LMA.
  • IA é parte ativa do processo de geração de código.
  • O time aceita acesso direto ao DbContext na camada de aplicação.

Considere outra quando

  • Você precisa trocar de persistência por agregado dentro do mesmo módulo. Aí o Repository volta a pagar aluguel — na LMA, a troca é por módulo inteiro.
  • O domínio tem complexidade combinatória extrema — motor de regras de seguro, tributação, cálculo atuarial. DDD ortodoxo com camadas explícitas serve melhor.
  • Múltiplos runtimes/UIs compartilham a mesma lógica de aplicação, não só de domínio (web + desktop + CLI + mobile com a mesma orquestração).
  • Você precisa de rastreabilidade extrema entre regra de negócio e código, em ambiente altamente regulado.
  • O time tem aversão estrutural a DbContext na aplicação. É questão cultural legítima — não vale impor.
  • O projeto será integrado a um codebase que já segue Clean Architecture rigorosa. Misturar estilos cria confusão.

05 — Balanço

O que você ganha e o que você paga.

Toda decisão de arquitetura é uma troca. Estas são as da LMA, sem maquiagem: o que ela otimiza e o preço que cobra por isso.

Prós

  • Feature inteira em uma pasta. Ação, Request, Response e Validator lado a lado. Nada de caçar 12 arquivos em 4 projetos.
  • Menos código para o mesmo resultado. Sem Repository, sem Writer, sem MediatR, sem AutoMapper, sem DTO em pasta central.
  • Regras validadas pelo build. A separação física impede a violação em vez de detectá-la em revisão.
  • Onboarding curto. O vocabulário é fixo: classe = verbo, método = Execute, retorno = Result<T>.
  • Escala por adição. Funcionalidade nova é pasta nova. Não se mexe em Ação existente (OCP na prática).
  • Múltiplos bancos por módulo sem ginástica — cada módulo aponta para o workload certo.
  • IA erra menos. Estrutura previsível e decisões já tomadas reduzem a variação inventada pelo modelo.
  • Teste que reflete produção. Integração via WebApplicationFactory, sem mock de banco.

Contras

  • Sem unitário puro na Ação. Sem Repository não há o que mockar — o teste da Ação é de integração. O unitário sem mock fica no Domain.
  • Acoplamento consciente ao ORM. Trocar o mecanismo de persistência de um módulo é refactor real, não troca de implementação.
  • Sem camada de aplicação reutilizável. Se outro runtime precisar da mesma orquestração, não há Application layer para compartilhar.
  • Alguma duplicação entre fatias. Ações não se chamam. Lógica repetida só sai por Domain Service — e nem tudo cabe lá.
  • Choque cultural. Times formados em Clean Architecture costumam estranhar o DbContext na Ação.
  • Disciplina de leitura. Sem Repository, consulta pesada mal escrita vaza direto para dentro da Ação.
  • Ecossistema jovem. A LMA é da Leanwork: menos material de terceiros, menos respostas prontas no Stack Overflow.
A inversão de dependência na LMA é seletiva: existe onde a volatilidade é real (gateways, storage, mensageria) e não existe onde ela é teórica (banco). Não é SOLID pela metade — é SOLID aplicado onde ele se paga.

06 — Geração assistida

Desenhada para o par humano + IA.

Não se trata de arquitetura para a IA substituir gente. Trata-se de reconhecer que o par humano + IA é a unidade real de produção de código hoje — e que otimizar só para um dos dois desperdiça o outro.

A fricção

  • Decisões abertas demais. “Isso é Use Case ou Service?” Cada pergunta sem resposta única é um ponto onde o modelo inventa uma variação diferente por feature.
  • Estrutura dispersa. Uma feature toca de 8 a 15 arquivos em 4 projetos. Muito contexto para carregar, muito caminho para errar.
  • Vocabulário variável. Handle, Execute, Process, Run. XxxHandler, XxxService, XxxUseCase. O modelo pula entre estilos.

A resposta da LMA

  • Estrutura rasa e previsível. Toda Ação vive em Modulos/{Modulo}/{Acao}/. O modelo sabe onde criar e onde procurar.
  • Vocabulário fechado. Classe = verbo de negócio. Método = Execute. Retorno = Result<T>. Não há o que inventar.
  • Guardrail de compilador. Tentar importar EF no Domain não compila. Não é “o review pega depois”: é erro de build imediato.
  • Validação e roteamento centralizados. Menos código gerado, menos chance de esquecer.

Suporte a IA já vem no template

Todo projeto gerado traz uma pasta .claude/ configurada. O Claude Code carrega tudo automaticamente, sem instalação. O CLAUDE.md na raiz também serve Cursor, Copilot e afins.

3 skills

lma-create-action, lma-add-module e lma-refactor-to-rich. Basta dizer “criar ação para listar clientes” e a fatia inteira sai no padrão.

/lma-docs, /lma-review e /lma-init para consultar a arquitetura, revisar e inicializar.

08 — FAQ

Perguntas diretas.

As dúvidas que aparecem em toda primeira conversa sobre a LMA — com a resposta curta. O documento completo tem 20 seções e vai junto em todo projeto gerado.

Sem Repository, como testo uma Ação isoladamente?

Você não testa isoladamente. A Ação é testada por integração, com WebApplicationFactory e Testcontainers. A lógica pura, testável sem mock, vive no Domain — entidades e Domain Services — e essa sim tem teste unitário.

Posso usar EF e Dapper no mesmo projeto?

Sim, e é encorajado. EF para escrita e leitura com produtividade; Dapper para leituras de alta performance — relatórios, listagens pesadas. A Ação injeta o que precisar.

Posso ter múltiplos bancos por módulo?

Sim — é um dos casos em que a LMA brilha. Cada módulo pode ter seu próprio DbContext ou conexão apontando para o banco mais adequado ao workload: Catalogo em Postgres, Auditoria em Mongo, Analytics em ClickHouse.

Quando os bancos são diferentes, a separação é ainda mais natural: não há como uma Ação de Analytics escrever, por engano, em tabela do Catálogo.

Como faço uma transação que envolve gateway de pagamento?

Com db.Database.BeginTransactionAsync(ct) explícito na Ação. Persista o pedido como pendente, chame o gateway e, conforme o resultado, faça commit ou rollback. O controle transacional fino é responsabilidade da Ação.

Onde fica a lógica de extrair o ClienteId do JWT?

Estritamente no Endpoint. A Ação recebe ClienteId já limpo no Request e nunca vê HttpContext ou ClaimsPrincipal.

Como dois módulos compartilham uma regra de negócio?

Via Domain Service em MinhaApp.Domain. As duas Ações usam o Domain Service. Ações nunca se chamam diretamente.

O Validator roda dentro da Ação?

Não. Roda automaticamente no IEndpointFilter aplicado ao grupo de endpoints, antes da Ação. Se falhar, retorna 400 e a Ação nem é chamada.

Como registro as Ações no DI?

Uma linha por Ação — AddScoped<ProcessarPedido>() — ou via scan de assembly, registrando todas as classes do namespace Modulos. Em projeto grande, o scan reduz boilerplate.

A LMA serve para MVP rápido ou só para projeto grande?

Os dois. No MVP você começa com o Domain quase vazio e poucos módulos na API. A estrutura é a mesma de um projeto grande, só com menos arquivos. Não existe “versão simplificada da LMA” — ela já é simples.

Por que dois projetos físicos desde o dia 1?

Porque separar depois é caro e ninguém faz. Começar com dois deixa o compilador como guardião desde a primeira linha, e o custo inicial é zero — um dotnet new classlib a mais. Para IA gerando código, essa barreira física previne a maior parte dos erros de dependência.

Qual a relação com a LVA?

A LMA consolida a Lean Vertical Architecture com cinco mudanças estruturais: dois projetos físicos obrigatórios; roteamento centralizado por módulo; unificação de Reader e Handler numa única classe de Ação; eliminação completa de Repository e Writer; e validação automática via IEndpointFilter.

Cada mudança tem dupla justificativa — simplifica para o humano e reduz a superfície de erro para a IA.
